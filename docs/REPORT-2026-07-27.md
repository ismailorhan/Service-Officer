# Another Windows machine, and the four bugs it exposed — 2026-07-27

Eight commits. Everything below was measured on real machines — a Windows 11
client and a SAP/SQL server in the `SC` domain, reached from this workstation in
`CT.CORP` — and every fix is locked down by a test that fails without it.

Build **2.0.0.26** is installed and running. Tests: **331 passing**.

The evening's shape: adding a second Windows machine to manage worked in about
twenty minutes, and then spent five hours proving that four separate things had
been quietly wrong for as long as the feature had existed.

---

## 1. Signing in to another Windows machine as a named account

The service manager takes no credentials — the RPC leaves as whoever the process
is — so a remote Windows machine was only manageable by someone who was already an
administrator on it. Across a forest boundary that is nobody: `CT\ismail.orhan` on
`SC-WIN11-CLIENT` is refused with error 5 whatever rights it holds at home.

`Sign in method` now offers the signed-in account, which needs nothing set up, or a
user name and password. Windows has no "connect as" argument to add, so a session
is established first — `\\HOST\IPC$` as `DOMAIN\account`, the program's version of
`net use` — and every later call rides on it. `WNetAddConnection2` rather than
`LogonUser` and impersonation, because a session belongs to the logon session and
one is enough for the poller, the action threads and the watcher together;
impersonation is per-thread and would have to be repeated on each.

Refusals are sentences. "1326" is not something to put in front of a person, and
the one that needs explaining is 1219: Windows allows one account per machine at a
time, so a mapped drive someone left open wins and the configured account is
refused. That is a dead end with a fix, and the fix is in the message.

Proven live, cross-domain: *"10.77.3.112 answered. Signed in as SC\ismailorhan.
Services can be started and stopped."*

## 2. The field names, and the machine's own identity

`Called` / `Reached as` / `Address` / `Account` / `Sign in with` said what the app
thought rather than what the field is. They are **Description**, **Target type**,
**Host**, **User** and **Sign in method**, and the method now comes above the User
and Password it asks for — the other way round put "User" above the choice that
decides whether a user is wanted at all.

The machines list was showing `machine.name`, which is not a name anybody chose to
see: it is the id the services point at, fixed when the machine was added. So a
machine added as "sd" and then described as "hanadev" went on reading
"sd (hanadev)", and the Description field looked broken. Showing the id as a
read-only row was the first attempt and it was worse — it answered "what is sd" by
raising "so which of these two names matters". It is plumbing, and it stays out of
sight.

## 3. Four bugs, each with a number attached

**Sixty-three seconds to read one service's status.**

| | |
|---|---:|
`OpenSCManager`, three times over | 21032 ms, 21022 ms, 21033 ms |
`EnumServicesStatus` on a held handle | 28 ms, 18 ms, 19 ms |
`OpenService` + `QueryServiceStatus` on a held handle | 7 ms, 7 ms, 6 ms |

All of the cost is opening, and the code opened afresh for every question — status,
start type and pid are three. The connection is held per machine now and reopened
only when a handle goes stale: **63100 ms → 9 ms**. The 21 seconds itself is
Windows' SYN retry budget against a firewalled dynamic RPC port; `sc.exe` pays the
same 21.1 s.

**A frozen window.** Priming, the thirty-second start-type sweep, Refresh, the
service picker and Test connection each walked every service and asked its machine
directly, on the thread that paints. On this computer that is a fraction of a
millisecond; on another one it was fifteen seconds for a service list and
forty-two for a firewalled refusal, each of them a window saying "Not Responding".
The rule now: **the UI thread only ever asks this computer.** Everything else goes
through the poller, an action thread or the monitor.

**Four SUSE services reading "Unknown".** The SSH transport set `push` from whether
the account could *read* the journal, and a machine that claims push is excluded
from polling. Nothing in this app follows a journal, and root can always read one.
It had been covered up by the priming pass asking each service directly — right
once, then quietly frozen — so taking that off the UI thread turned a hidden bug
into a visible one.

**A restart that stopped a service and reported success.**

    stop asked           0.0s  ->  Stopping
    Stopped             61.0s
    running again       62.8s

Sixty-one seconds to stop a Tomcat, against a thirty-second budget. When it ran out
the code started it anyway, and Windows answers a start request with 1056, "already
running", for a service in any state other than Stopped — Stopping included. 1056
was on the list of errors meaning "nothing to do", so the refusal was swallowed and
the service finished stopping in peace. Two-minute budget, checked waiting, and a
failure that "nothing to do" cannot forgive. Real action failures are now logged;
only the harmless ones were, which is how this left nothing behind but a line
calling it harmless.

## 4. Whether a machine is answering, on the machine's own row

The reason the third bug took an evening is that "Unknown" on a service has several
explanations and there was nowhere to see which. A machine's row now says:
**connected · answered 3s ago**, **no answer, last tried 12s ago**, or **not asked
yet** — a state of its own, and the one that was in play. The transport's own words
go in the tooltip: put in the summary,
`pywintypes.error: (1722, 'OpenSCManager', …)` made the row wider than the window,
pushed every chip out of sight and grew a horizontal scrollbar.

## 5. Housekeeping

Nine dead imports removed, found with an AST sweep rather than by eye — including
`win32serviceutil`, which stopped being used the moment start/stop/restart moved
onto the held connection.

Saving settings dropped every connection, so changing the theme cost twenty-one
seconds of "Unknown" on the remote machine. Only the machines whose settings
actually differ are let go of now; the panel drops one itself when a password is
stored, because the config cannot show that the value behind an unchanged entry
name has changed.

The UI paths that repeat were measured, and the answer to "should we optimise them"
is no: `apply_states` 0.05 ms, the hover card 1.09 ms, the machines list 3.17 ms
every three seconds. The expensive things in this application are all on the other
side of a network.

## 6. What was decided, and what is planned

A hub. One Windows service owning the config, the connections and the history, with
the tray app as its first client and a browser page as its second — and **no agents
on managed machines**, because SSH reads four services in 64 ms while installing
nothing, and the Linux targets are headless servers whose owner does not want our
software on them.

The 2026-07-25 design in `DECISIONS.md` said the opposite (agents reporting inward)
and has been struck through with the measurements that changed it. The task-by-task
plan is `docs/superpowers/plans/2026-07-27-hub-service-and-clients.md`; it starts
with the one thing that can break what already works — moving the engine out of the
application object — and says so.

## What is still open

- **`10.77.3.110`** is manageable now, but only because four firewall rules were
  enabled on it by hand. `10.77.3.112`, being a Windows Server, needed nothing —
  servers default to allowing remote management and clients do not. Worth knowing
  before someone tries this on a customer's workstation.
- **The 21-second first connection** to `10.77.3.112` is paid once per app run and
  disappears if the *Remote Service Management (RPC)* rule is enabled there. Not
  our bug, but our slow start.
- **A password is stored on this workstation** for the `SC` machines. Running the
  hub as a domain service account in that domain would remove the need entirely —
  the first thing to decide when the hub is built.
