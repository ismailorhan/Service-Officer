# The hub, and the seven bugs that only appeared when it was used — 2026-07-28

Four commits, finishing the thirteen-task plan written on 2026-07-27. The engine now
runs as a Windows service, the tray application can read it over HTTPS instead of doing
the work itself, and one installer sets up either half or both.

Tests: **470 passing**, in 101 s — the whole suite used to take 197 s, and
the difference is bug 2. Version **2.2.0**. Both halves built and packaged.

The shape of the day: the architecture was already decided and mostly written, so most
of the time went into the things that only show up when a person actually uses it — a
token pasted into a real browser, a built exe run against a real TLS hub, a test that
failed only under load. Seven of those, each a real defect, each now held down by a test
that fails without the fix.

## The seven

### 1. A client added while the hub was running was refused

The worst of them, and it was found by pasting a real token into the real page.

The client list is cached to avoid a DPAPI decrypt per request — measured at 13.2 ms
against 0.27 ms to build a snapshot — and the cache was invalidated *on write*. But
`client add` is a console command in a **different process** from the service. The hub
never did the write, so it never dropped the cache, so every token issued after it
started was refused. The only cure would have been restarting the hub in the middle of
setting up a client.

The cache now carries the store file's `(mtime_ns, size)`:

| | Cost |
|---|---|
| `os.stat` on the store | 55 µs |
| warm token check, including the stat | 59 µs |
| cold check (DPAPI decrypt) | 13.2 ms |

240× cheaper than what it saves, so it is taken on every request. Proved with a real
second interpreter writing the same store — not a monkeypatch, because the bug *was*
the second process.

### 2. `stop()` did not stop, and the next `start()` did nothing

A reconnect test failed in a build that had passed twenty minutes earlier. Under load it
was slower, and slower exposed two separate bugs.

`HubClient.stop()` set a flag the reader only looks at between lines, and an idle event
stream says nothing for a keepalive interval — **20.1 s measured**. Worse, `start()`
refuses to run while the old thread is alive, so a stop that had not finished made the
next start a silent no-op: the client sat reading a stream nobody was managing.

It now shuts the socket down, which is the only thing that interrupts a blocked read.
Holding the socket meant using `http.client` for that one request instead of `urlopen`:
an SSE response has no length and no chunked framing, so `getresponse()` hands the socket
to the response and forgets it, and `urlopen` never exposed it at all.

| | Before | After |
|---|---|---|
| `stop()` | 20.1 s | under 0.1 s |
| the client's test file | 328 s | 30 s — the teardowns were the whole difference |
| `start()` after `stop()` | silently did nothing | connects |

It also runs on the way out of the application, where twenty seconds is a window that
does not close.

### 3. A gap in the handshake where a change went to nobody

The other half of that failure. The client fetched a snapshot, announced itself
connected, *then* opened the event stream — and a change published in that window went
nowhere. Because a store publishes only *changes*, the client did not show a stale value
for a moment; it showed the wrong one until that same service happened to change again.

The order is now stream → snapshot → events. The hub queues per listener from the moment
a stream opens, so anything during the snapshot arrives after it, in order, on top of a
store that already has the snapshot under it.

### 4. The browser page was about to be the fourth surface to disagree

`st.effective()` exists because the flyout, the hover card and the tray icon each worked
out "Running but failing its checks means *Not responding*" separately, and then
disagreed with each other about the same service at the same moment. The new page had a
lookup table of its own — the same mistake, one process further away.

The hub now sends `state_label` and `state_category` on every row and the page draws what
it is told. Its counter reads the category too, so "2 of 4 running" cannot contradict the
row beside it — which is the identical bug fixed in the panel on 2026-07-26.

### 5. `--store-only` never pinned the certificate

Found by running the **built** exe against a real TLS hub, which is the only place it
could show: the unit test used a fake client that reported success.

The installer's `/HUBURL /HUBTOKEN` path stored the token and the address and left the
fingerprint blank, so the certificate was pinned by whatever answered on first launch
instead of by the hub the administrator deployed against. Both are trust-on-first-use;
only one of them is under the administrator's control. It pins at install time now, and
an unreachable hub is not a failure — the token is kept and the reason is printed.

### 6. The service would not have started at all

Found by reading `hub.py` once more before packaging it, and it is the most embarrassing
of them because nothing that was run all day could have found it.

The SCM starts a service by launching the exe **with no arguments** — nothing on the
command line says which service it is — and the process has about thirty seconds to
connect back through `StartServiceCtrlDispatcher`. `main()` had no branch for that, so the
launch fell through to pywin32's `HandleCommandLine`, which found no command, printed
usage and exited. Windows reports that as **error 1053, "the service did not respond in a
timely fashion"**, which says nothing about the cause — and it only happens on a machine
where the service is really installed, so `--console` would never have shown it.

`hub.py` had no test file. It has one now (`tests/test_hub_service.py`, seven tests, one
per way of being started), and the fix was verified the only way worth trusting: by
removing it and watching that test fail.

### 7. The plan said move the manifest; the plan was wrong

`--uac-admin` was to move from the tray application to the hub, because "the tray
application no longer touches a service manager". True of a client of a hub, **false of
the single-machine install everybody has today**, which drives this computer's SCM
directly. Shipping it as written would have turned every button in that install into
*access denied* — silently, because a query needs no rights and a control does.

So the manifest is gone and the question is asked at run time: elevate only when this
launch will do the work itself, which means no hub address configured and none being
passed. A client never prompts; an embedded install prompts exactly as it always did.

Also removed on the way past: `Config.hub.enabled`, which existed, defaulted to False and
was read by nothing. Installing the hub component is the decision to serve; a second
switch would only have made "the service is running and nothing answers" possible.

## What an existing installation does when it upgrades

Nothing, unless the hub component is ticked. The `services.json` in
`%ProgramData%\Service Officer` is exactly where the hub looks, so it becomes the hub's
config in place — nothing is migrated, moved or rewritten. A machine that installs both
components comes out already paired, with no token shown to anybody.

The history file gains one column by `ALTER TABLE` (schema v3), so existing rows survive.
An older build reading a newer file still works: steps only ever add.
